# Backlog

The live backlog. One row per item, ordered by what stands between the product and being sold safely — not by when it was noticed.

When an item is picked up it gets an execution spec in [`features/`](../features/README.md) and its row links to it. Reasoning behind each block is in [`docs/sot/`](./sot/README.md).

**This file is not where the next task is chosen.** It answers *what is missing and how much it matters*; the [build order](./sot/10-saas-roadmap.md#build-order) answers *what is next*, because it carries the dependencies between items and a priority column cannot. When the two disagree, **the chain wins** — a priority is a judgement and can be revised, a dependency cannot. There is already one live case: *shared rate-limit store (Redis)* sits in P1 but needs the Redis that arrives with the P2 job queue.

Last reviewed: **2026-08-29**.

## P0 — Blocks any real customer

**Empty.** The data-loss defect, the unthrottled public write paths, the ReDoS surface, the red E2E suite, the unenforced Node version and the publicly served uploaded PDFs are all closed ([`features/0001`](../features/0001-stable-field-ids-and-safe-bulk-save.md)–[`0006`](../features/0006-signed-expiring-urls-for-uploaded-pdfs.md)). Security headers and a CSP ([`features/0007`](../features/0007-security-headers-and-csp.md)) and session hardening ([`features/0008`](../features/0008-session-hardening.md)) are closed too. **There are no High findings left open.** What remains in P1 is privacy and operational work — of it, structured logging (S9) is the one that unblocks the most, because CSP reporting and any answer to "what happened to our submission at 14:32" both wait on it.

## P1 — Security, privacy and operational readiness

| Item | Why | Reference |
|---|---|---|
| Shared rate-limit store (Redis) | The limiters use an in-memory store, so the effective limit multiplies by replica count and resets on every deploy. Fine at one replica; not fine the moment the service scales out. Depends on the Redis that arrives with the job queue | [07-security](./sot/07-security-and-privacy.md) · [`features/0002`](../features/0002-rate-limiting-on-public-write-paths.md) |
| Account-level lockout on repeated failed logins | Per-IP limiting does not stop credential stuffing distributed across hosts. Deliberately deferred: a per-account limiter without an unlock path lets anyone lock a named user out by spamming their address, so it needs the notification and unlock flow designed with it (S10) | [07-security](./sot/07-security-and-privacy.md) (S10) |
| A global fallback rate limiter | Only the three unauthenticated write paths are limited. Everything else — including `GET /api/forms/public/:shareId` and `/uploads` — is unthrottled. Picking a global number that does not break the editor's legitimate bursts needs traffic data we do not have yet | [07-security](./sot/07-security-and-privacy.md) |
| No UI for authoring a field `pattern` | `FieldPropertiesPanel.vue` has no pattern input, so the only way to set one is the API. Now that patterns are validated and a useful `400` names the problem, a UI is worth having — it needs live validation and must explain that lookahead/lookbehind/backreferences are unsupported | [`features/0004`](../features/0004-safe-author-supplied-regex.md) |
| Frontend still compiles patterns with native `RegExp` | `frontend/src/composables/useFormValidation.ts:42` runs the author's pattern in the respondent's browser. Lower severity than the server case — it burns the respondent's own tab, not shared infrastructure, and it is already `try/catch`-wrapped — but it should agree with the backend's engine, or the two will disagree about which patterns are valid | [`features/0004`](../features/0004-safe-author-supplied-regex.md) |
| `Form.pdfUrl` is an unconstrained client-supplied string | `createFormSchema` / `updateFormSchema` accept any `z.string()`, so an author can point their own form at another author's uploaded filename. Filenames are unguessable, so this is obscurity, not a control — and since [`features/0006`](../features/0006-signed-expiring-urls-for-uploaded-pdfs.md) the API will mint a valid signed URL for whatever filename is in the column. The fix is to verify at write time that the file came from an upload this user made, which needs an uploads table | [07-security](./sot/07-security-and-privacy.md) |
| CSP violation reporting | The SPA's policy has no `report-uri`/`report-to`, so a policy the app quietly breaks in someone's browser is invisible. Needs somewhere to send reports and something that reads them, which is the structured-logging item below — do them together | [07-security](./sot/07-security-and-privacy.md#what-the-spa-policy-does-not-cover) · (S9) |
| `style-src` still needs `'unsafe-inline'` | Measured in [`features/0007`](../features/0007-security-headers-and-csp.md): 373 violations from `style` attributes (Vue `:style`, the editor's positioned overlays) and 50 from PrimeVue injecting `<style>` at runtime. Splitting into `style-src-elem`/`style-src-attr` grants the same permission and was tried. Narrowing it means changing how the app styles things — worth doing only alongside a deliberate styling change, not on its own | [07-security](./sot/07-security-and-privacy.md#what-the-spa-policy-does-not-cover) |
| Session listing and per-session revocation | A user cannot see the sessions on their account or end one from another device, and there is no idle timeout — a refresh token lives its full 7 days whether used or not. `refresh_tokens` already carries everything needed (`family`, `createdAt`); what is missing is an endpoint and a screen | [07-security](./sot/07-security-and-privacy.md#what-the-session-model-does-not-cover) · [`features/0008`](../features/0008-session-hardening.md) |
| Nothing migrates the integration test database locally | CI runs `prisma migrate deploy` against `vuepdf_test` before the integration suite; no local script does, so the first run after any migration fails with `relation does not exist` and looks like a broken test rather than a missing step. Hit while building [`features/0008`](../features/0008-session-hardening.md). A `pretest:integration` step would close it | [09-quality](./sot/09-quality-and-testing.md) |
| Structured logging (`pino`) with request ids and redaction | No way to answer "what happened to our submission at 14:32"; also the only way to see the silent PDF-embed failures | [08-operations](./sot/08-operations.md) · (S9) |
| Account deletion and per-account data export | GDPR erasure and portability; neither exists | (S8) |
| Response retention policy and a respondent privacy notice | IP and user agent are collected from respondents with no notice, no limit and no actual anti-abuse use | (S7) |
| Password policy, lockout, breach check | 6-character minimum, unlimited attempts | (S10) |
| ESLint flat config, then lint in CI | `npm run lint` currently succeeds while linting nothing, because no workspace defines a `lint` script and there is no `eslint.config.js`. Type check and build now run in CI; lint is the remaining piece | [09-quality](./sot/09-quality-and-testing.md) |
| Validate all configuration at boot with Zod | Only `JWT_SECRET` is checked; a wrong `BASE_URL` silently produces broken PDF links | [08-operations](./sot/08-operations.md) |
| Production build must generate the Prisma client before pruning devDependencies | `backend`'s `postinstall` runs `prisma generate`, but `prisma` is a devDependency, so `npm ci --omit=dev` would run the hook without its CLI. Harmless today (no deploy pipeline exists), and a trap for whoever writes one | [08-operations](./sot/08-operations.md) |
| Automated backups with a tested restore | None exist; recovery time is unknown | [08-operations](./sot/08-operations.md) |
| Error tracking on API and SPA | Browser-side editor failures are invisible today | [08-operations](./sot/08-operations.md) |

## P2 — SaaS foundations, design and go-to-market

Most of this is a dependency chain — see the build order in [10-saas-roadmap](./sot/10-saas-roadmap.md).

**Two things here are not.** The **landing page** blocks nothing and nothing blocks it; the roadmap keeps it as a [parallel track](./sot/10-saas-roadmap.md#parallel-track-the-landing-page) rather than pretending it has a place in the chain. And the rows about facts and prices are decisions for a person, not work for an engineer — they are here because they block a launch just as hard.

| Item | Why |
|---|---|
| Email delivery for invitations | There is no mail provider at all, so an invitation is a link the inviter copies and sends themselves. It works, and it puts the burden on the customer — and if they lose the link before sending it, the invitation is unusable and must be reissued. Wants the job queue from step 9 of the [build order](./sot/10-saas-roadmap.md#build-order) for retries and a delivery record | [07-security](./sot/07-security-and-privacy.md#invitations-are-bearer-capabilities) · [`features/0010`](../features/0010-member-invitations-and-role-enforcement.md) |
| No audit of who invited, removed or promoted whom | `Invitation.invitedByUserId` records who sent an invitation and nothing records who removed a member or changed a role. For a B2B buyer that is a due-diligence question, and after an incident it is the only way to answer "who let them in". Wants structured logging (S9) first | [08-operations](./sot/08-operations.md) · (S9) |
| An organization can outlive its last member — **via account deletion only** | [`features/0010`](../features/0010-member-invitations-and-role-enforcement.md) closed the two reachable-from-the-app paths: the last owner can no longer demote or remove themselves. What remains is `Membership.user` cascading on **user deletion**, which would still strand the organization and its forms with nobody able to reach them. Needs a rule decided alongside account deletion (S8), which is the only thing that can trigger it | [03-domain-model](./sot/03-domain-model.md) · [`features/0009`](../features/0009-organizations-own-resources.md) |
| **Decide the landing technology** | Nobody has chosen, and if this stays undecided it gets decided by whoever opens an editor first. It is a real decision because the landing has requirements the SPA does not: it must be indexable, it must be fast on a cold first visit, and it is the one page whose audience has never heard of us. The options, their real costs and a recommendation are in [02-architecture](./sot/02-architecture.md#the-landing-page-an-open-decision-not-implemented). Blocks the landing build and nothing else |
| **Build the landing page** | The commercial front door, and it does not exist. Designed already — desktop and phone artboards, one offer, one repeated action (*Start free*), and the hook is the differentiator that is already built: a PDF that is already a form keeps its fields on upload. A **parallel track**, not a step in the chain — it blocks nothing and nothing blocks it | [05-frontend-patterns §8](./sot/05-frontend-patterns.md) · [01-product-and-market](./sot/01-product-and-market.md) |
| Facts the landing cannot ship without | The canvas leaves eight things bracketed on purpose, because they are decisions rather than design: `[SUPPORT EMAIL]`, `[LEGAL ENTITY NAME]`, `[REGISTERED ADDRESS]`, `[CUSTOMER LOGO]`, and the `[NAME]` / `[ROLE]` / `[COMPANY]` / `[CITY]` of one real reference. **The prices on it are also not a decision anyone has taken** — they match the Plan & usage screen and were drawn to make the page whole. None of this is engineering work and all of it blocks launch |
| The canvas promises role semantics the API does not enforce | The **Members & roles** artboard says a member sees "only the forms they created". `backend/src/routes/forms.ts` scopes forms by organization and checks *membership*, not role, so every member reaches every form and every response in the organization. [`features/0011`](../features/0011-adopt-the-design-system.md) made `MembersView.vue` state what the guards actually do rather than what the canvas says, which is honest but is not the product the design describes. Decide which one is right — per-creator scoping is a real B2B expectation, and shipping the canvas's wording without it would be telling a customer their data is partitioned when it is not |
| No endpoint returns an organization's name, so the sidebar has no switcher | The canvas puts an organization switcher at the top of the sidebar and `frontend/src/services/organization.ts` can only list members and invitations. [`features/0011`](../features/0011-adopt-the-design-system.md) left the space empty rather than invent a name. Blocks nothing today because everyone has exactly one organization; blocks the switcher the moment anyone has two |
| `Plan` catalogue + entitlements service, `402` on limit reached | Validates limit UX before money is involved |
| Stripe integration + `Subscription` | Revenue |
| Per-file revocation for signed PDF URLs | Today revocation is all-or-nothing: rotate `JWT_SECRET` (invalidating every outstanding link) or delete the file. Withdrawing access to one PDF while leaving others valid needs a database-backed nonce or key version per file. Cheap to add alongside the uploads table above |
| Object storage (S3/R2) for PDFs | Blocks running more than one replica or redeploying on ephemeral disk |
| Job queue (BullMQ + Redis) for PDF extraction and embedding | Currently synchronous inside the request; timeout risk on large PDFs |
| Public API with per-organization API keys | Requires stable field ids first |
| Webhooks with signed payloads, retries and a delivery log | Same prerequisite |
| Usage metering for responses per month | Needed for plan limits, and it must agree with the invoice |

## P3 — Product and technical debt

| Item | Why |
|---|---|
| PDF round-trip test: editor position → embedded AcroForm position | Nothing verifies the canvas-to-PDF scale coupling; it silently breaks on any zoom change | 
| Move the canvas/PDF scale into the data instead of two hard-coded constants | `DEFAULT_SCALE = 1.5` exists independently in both workspaces |
| Share request/response types between backend and frontend, generated from Zod | The two currently redeclare the contract by hand |
| A local `vuepdf` database from before the baseline is silently a decade behind | The dev database on this machine had **none** of `organizations`, `memberships`, `refresh_tokens` or `invitations`, and `prisma migrate status` reported all seven migrations unapplied including `0_baseline` — so nothing had ever told anyone. Registration 500s, and the E2E suite reports it as an application failure. The recovery is documented in [08-operations](./sot/08-operations.md#database-migrations) (`migrate resolve --applied 0_baseline`, then `migrate deploy`) but nothing points at it when it happens. Hit while building [`features/0011`](../features/0011-adopt-the-design-system.md); `npm run check:node` already exists as the place a check like this would belong | [08-operations](./sot/08-operations.md) |
| The E2E suite silently reuses a dev backend, and then 25 tests fail for the wrong reason | `playwright.config.ts` sets `reuseExistingServer: !process.env.CI`, so a backend already running on `:3000` from `npm run dev` is adopted — **without** the `RATE_LIMIT_*: 100000` overrides the config passes to the server it starts itself. Registration then hits the real limiter and every test that registers or logs in fails with a timeout on `waitForURL(/\/dashboard/)`, which looks exactly like an application bug. Hit while building [`features/0011`](../features/0011-adopt-the-design-system.md). Either fail fast when the adopted server is not in test configuration, or use a distinct port | [09-quality](./sot/09-quality-and-testing.md) |
| The local integration database has to be **created** as well as migrated | The existing row below says nothing migrates `vuepdf_test` locally. It is worse than that: nothing creates it either, and the failure is `Database \`vuepdf_test\` does not exist` across all seven specs. The full local incantation is `docker exec vuepdf-db psql -U postgres -c "CREATE DATABASE vuepdf_test;"` then `DATABASE_URL=…/vuepdf_test npx prisma migrate deploy`. A `pretest:integration` script should do both | [09-quality](./sot/09-quality-and-testing.md) |
| A Spanish toast survives in `FormFieldItem.vue` | `"Error al guardar posición"` / `"No se pudo guardar la nueva posición del campo"` on a failed drag-save, in an otherwise English UI. Left alone by [`features/0011`](../features/0011-adopt-the-design-system.md) because the i18n row below says to fix this with a layer rather than string by string, and one more hand-translated string makes that layer harder to justify |
| i18n layer for UI copy | Spanish placeholders remain in an otherwise English UI |
| Server-state library (TanStack Query) for reads | Every store hand-manages loading, error and caching |
| Evaluate VueUse for `useDragAndDrop`, `useGridOverlay`, `useToolbarDrag` | Case by case; some encode editor-specific behaviour |
| Soft delete or export prompt before `DELETE /api/forms/:id` | Cascades to every response with no undo |
| `DELETE /api/forms/:formId/fields/:fieldId` still hard-deletes answers | The bulk save now archives a field that holds responses; the individual delete still cascades them away. Deliberately left as an explicit user act in [`features/0001`](../features/0001-stable-field-ids-and-safe-bulk-save.md), but the two paths should agree — probably by archiving here too, with a confirmation that says how many answers are affected |
| No E2E coverage of opening a saved form for editing | `handleEdit` in `FormsList.vue` and `FormsManagementView.vue` downloads the form's PDF and loads its fields, and no test touches it. [`features/0006`](../features/0006-signed-expiring-urls-for-uploaded-pdfs.md) changed both and had to be verified by hand against the running app. One Playwright test would cover the whole path |
| No UI for archived fields | A field archived by a save is invisible to its owner except as a toast at save time and a column in the responses table. No list, no un-archive, no way to tell an archived column from a live one in the dashboard |
| The bulk save's concurrency guard is untested | The `SELECT … FOR UPDATE` in the bulk handler is what stops a response submitted mid-save from having its answer cascaded away. Nothing exercises it — a real test needs two connections and deliberate interleaving |
| Nothing exercises a migration against a database that already holds data | CI applies migrations to a fresh database only, so a migration that is fine on empty tables and wrong on populated ones passes |
| Virus scanning on uploads | Files are stored and served back from our own origin |
| Real readiness probe | `/health` returns `ok` with the database down |
