# CLAUDE.md

Instructions for Claude Code sessions in this repository. Read this before changing anything structural.

## What this is

**VuePDF Forms** — a micro-SaaS that turns a PDF into a fillable online form and collects structured responses. Vue 3 SPA plus an Express/Prisma/PostgreSQL API, in an npm-workspaces monorepo.

It is being built to be sold, B2B and B2C. That changes what "done" means: data loss, missing authorization and unbounded public endpoints are not backlog items to get to eventually — they are the product not working.

## Commands

```bash
npm run dev                      # both workspaces (docker-compose up -d first, for PostgreSQL)
npm run test:frontend            # Vitest, 47 specs / 393 tests beside the source
npm run test:backend             # Vitest + supertest over a mocked Prisma, 21 specs / 248 tests in backend/tests/
npm run test:integration         # Vitest + supertest over a REAL PostgreSQL, 24 specs / 221 tests in backend/tests/integration/
npm run test:e2e                 # Playwright, 53 tests; starts both apps itself
npm run build --workspace=frontend   # includes vue-tsc type checking
cd backend && npx tsc --noEmit       # backend type check
cd backend && npm run typecheck:tests # checks tests/fixtures/ against the Stripe SDK's own types
```

This repository requires Node **`>=22.12.0`** (see `.nvmrc`). It is enforced, not suggested: `npm ci` fails on an older Node, and every test/build script runs `scripts/check-node.mjs` first — which also verifies that the generated Prisma client and the native `re2` binary load. If something looks inexplicably broken, run `npm run check:node`.

`npm run lint` exists but lints nothing — there is no ESLint config in the repo. Do not treat a passing `lint` as a signal.

## Hard rules

1. **Never assert a fact about this code from memory or inference. Open the file.** A wrong claim in the SoT is worse than no claim, because the next session trusts it.
2. **Commits carry no `Co-Authored-By` trailer and no AI-authorship marker.** Explicit decision of the repository owner.
3. **Branch from `develop` with `--no-track`:**
   ```bash
   git checkout --no-track -b feature/NNNN-slug origin/develop
   ```
   Without `--no-track` the new branch's upstream is `origin/develop` itself, and a later push lands directly on `develop`, skipping the PR. Never commit on `develop` or `main`.
4. **Creating a local branch needs no confirmation. Pushing, opening a PR, and deleting a remote branch do** — every time.
5. **Before writing any `delete`, `deleteMany` or new cascade,** check the cascade map in [03-domain-model](docs/sot/03-domain-model.md) and answer: what customer data does this destroy, and did the user ask for that? Editing something is not consent to delete data collected through it.
6. **A mocked Prisma client cannot test database behaviour.** Cascades, constraints and rollbacks need a real PostgreSQL — that is what `backend/tests/integration/` is for (`npm run test:integration`). A green mocked test against broken code is how this project's data-loss defect shipped.
7. **File what you find.** A risk noticed while doing something else goes into `docs/BACKLOG.md` with a priority and a why — not into a sentence in the chat that disappears.
8. **Report outcomes as they are.** If tests fail, show the output. If part of the task was skipped, say which part and why. Do not describe partial work as finished.

## Current state, in one paragraph

Auth, form CRUD, the field editor, AcroForm extraction and embedding, the public form flow, the responses dashboard and CSV export all work. The bulk-save data-loss defect is fixed ([`features/0001`](features/0001-stable-field-ids-and-safe-bulk-save.md)): field ids are stable across saves, the editor's save is a diff, and deleting a field that holds answers archives it (`Field.deletedAt`) instead of destroying them. Prisma migrations are baselined; every schema change goes through `migrate dev` / `migrate deploy`. The five unauthenticated write paths are rate limited per IP (`backend/src/middleware/rateLimit.ts`); note that this depends on `TRUST_PROXY_HOPS` being right for the deployment. **Where the count lives is configuration** ([`features/0018`](features/0018-shared-rate-limit-store.md)): `REDIS_URL` unset means an in-memory counter per process — correct at one replica, and what every suite runs on — and set means one shared store, so the limit belongs to the service rather than to whichever replica answered. Two things about it are easy to get wrong. **A store failure rejects the request** (`passOnStoreError: false`, argued in [07-security](docs/sot/07-security-and-privacy.md)): a Redis outage is a loud, one-step-reversible outage rather than the silent removal of rate limiting from the whole public surface. And **the counters no longer forget** — restarting the API used to be the accidental unlock, so [08-operations](docs/sot/08-operations.md) carries the `redis-cli` command that clears one identity. Author-supplied field `pattern`s are compiled by RE2 through `backend/src/services/pattern-validator.ts` — never `new RegExp` at a call site — which removes the ReDoS surface and the 500-on-invalid-pattern defect. Uploaded PDFs are no longer served by `express.static`: they come only from `GET /uploads/pdfs/:token/:filename`, whose token is minted per read by `backend/src/services/pdf-url.ts` and expires after `UPLOAD_URL_TTL_SECONDS` ([`features/0006`](features/0006-signed-expiring-urls-for-uploaded-pdfs.md)) — the URL stored in `Form.pdfUrl` is always the unsigned canonical one, never a signature. **Where the bytes live is now configuration** ([`features/0016`](features/0016-object-storage-for-uploaded-pdfs.md)): `backend/src/services/pdf-storage.ts` is the only module that reads or writes them, and `PDF_STORAGE_DRIVER` selects `local` (this process's disk, the default, and what every test suite runs on) or `s3` (AWS, R2, MinIO). Three things about it are easy to get wrong. **Provider presigned URLs were deliberately not used** — redirecting to one would drop the CSP/`nosniff`/`X-Frame-Options` headers that neutralise attacker-supplied bytes, move expiry off `verifyPdfToken`, and break the `url.split('/').pop()` that three frontend call sites depend on; the bytes stream through the API instead. **Switching the driver moves nothing** — run `npm run storage:migrate` first, or every form uploaded before the switch loses its PDF. And **an unknown driver name refuses to boot** rather than degrading, because falling back to local disk would accept uploads and lose them at the next deploy. Embedding is a read-modify-write, so it is serialised per form *and* re-reads the fields inside that serialisation — the two halves together are what stop two overlapping saves discarding each other's work. **Where that runs is now configuration too** ([`features/0017`](features/0017-job-queue-for-pdf-embedding.md)): `REDIS_URL` unset means the embed runs inline in the request as it always has, and `REDIS_URL` set means `POST /api/forms/:formId/fields/bulk` enqueues a job that `npm run worker` — the same image, a second entrypoint — picks up. `backend/src/services/embed-queue.ts` is the only module that imports BullMQ, and the work itself is `backend/src/services/pdf-embed.ts`. Four things about it are easy to get wrong. **Only the embed moved**, deliberately: extraction on upload and on first read still runs inline because both responses *carry* the fields they extract and the editor draws them immediately — making those async is a product change with a UX attached, and it is filed. **Do not deduplicate with a stable job id per form** — BullMQ ignores an `add` whose id belongs to a job that is already running, so a save made during an in-flight embed would vanish and the PDF would sit permanently behind the database; every save enqueues its own job and a Redis lock per form is the serialiser, which is also what closes the cross-replica race the in-process lock could not. **Unset Redis is the default and the inline path stays**, so two code paths exist for one operation and both must work — the suites run the inline one and `tests/integration/pdf-embed-queue.spec.ts` runs the queued one against a real Redis, skipping unless `TEST_REDIS_URL` is set. And **with `REDIS_URL` set and no worker running, nothing fails**: no request errors, the queue just fills and every form's PDF quietly stops matching its fields, which is why [08-operations](docs/sot/08-operations.md) says how to tell whether a worker is alive. Both entrypoints install `backend/src/process-guards.ts`, which logs an unhandled rejection and stays up but logs an uncaught exception and exits — the asymmetry is deliberate. Security headers are set by `helmet` in `backend/src/app.ts` and the SPA carries a CSP built at build time in `frontend/vite.config.ts` ([`features/0007`](features/0007-security-headers-and-csp.md)) — note that a CSP on API responses would govern nothing, which is why there deliberately is not one, and that the PDF route overrides `Cross-Origin-Resource-Policy` because the SPA is a different origin. Sessions are a 15-minute access token held **in memory** by the SPA plus a rotating, revocable refresh token in an `httpOnly` cookie, backed by the `refresh_tokens` table ([`features/0008`](features/0008-session-hardening.md)) — logout revokes server-side, replaying an exchanged token kills the whole family, and the two cookie-authenticated routes (`/api/auth/refresh`, `/api/auth/logout`) are the only ones carrying a CSRF guard, because every other route authenticates with a header that cannot be set cross-site. **Forms are owned by an `Organization`, not a `User`** ([`features/0009`](features/0009-organizations-own-resources.md)): every authorization check resolves a `Membership`, `Form.createdByUserId` is provenance and never an authorization input, and a cross-tenant read is a `404` rather than a `403`. Registration creates a personal organization transactionally, so a B2C account is just an organization with one member. `Membership.role` is **stored but not enforced**, and deleting a user no longer destroys their forms — check the cascade map before assuming otherwise. Members join through an **invitation link the inviter copies and sends themselves** — there is no email service anywhere in this repo — which expires, is single-use and revocable, and refuses to be accepted by an address other than the one it names ([`features/0010`](features/0010-member-invitations-and-role-enforcement.md)). `Membership.role` **is** enforced now, by `requireRole` in `backend/src/middleware/membership.ts`, and an organization can never be left without an owner. Note the two rejection codes: not a member is `404`, a member with the wrong role is `403`. **Plans and entitlements are built** ([`features/0012`](features/0012-plan-catalogue-and-entitlements.md)): the catalogue is a frozen constant in `backend/src/services/plans.ts` (never a table), `Organization.planKey` says which entry applies until `Subscription` exists, and every limit is an explicit call from `backend/src/services/entitlements.ts` inside the handler — never middleware. Three things about it are easy to get wrong and are the reason it is spelled out here: **publishing is metered, not creating** (the design meters forms *published at once*, so drafting is free and unpublishing frees a slot); **`402` means a plan limit and `403` means a permission failure**, and they are never collapsed; and **a `402` must never reach a respondent** — the public form answers `404` and the public submit answers `403` with the wording a closed form gets, because a respondent is not the customer and the owner's billing state is not public. The response meter is `UsageCounter`, one row per organization per UTC month, claimed by an atomic upsert-and-compare inside the submission's transaction; it counts submissions *accepted in the period*, so deleting a form does not refund the month and it will legitimately disagree with `SELECT count(*)`. **`Plan.hasBranding` is wired** ([`features/0014`](features/0014-close-the-subscription-surface.md)): `GET /api/forms/public/:shareId` returns `showBranding`, one boolean derived on the server, and `PublicFormView.vue` renders the mark only when it is true. That payload is anonymous, so it deliberately carries no plan, no limit, no usage and no organization id — sending the plan and letting the client decide would publish the customer's billing state to every respondent. Note that `DEV_PLAN_KEY=dev` grants the entitlement, so the mark vanishes in local development. The seat limit (`assertCanInvite`) **is wired now** ([`features/0015`](features/0015-team-plan-and-purchased-seats.md)), into `POST /api/organizations/invitations`, and three things about it are the ones to know. **Seats count total people, not people beyond the owner** — the owner is a `Membership`, so Free's one seat means *you, alone*, and a Free or Pro account inviting a colleague gets a `402` that is the product working. **Team's seats are bought, not billed after the fact**: the customer sets the quantity in Stripe's portal, `Subscription.quantity` is read off the webhook and written nowhere else, and the effective limit is `max(catalogue floor, quantity)` — resolved by `seatLimitFor`, the one place in `entitlements.ts` that reads a billing table, for one plan family and one column. Pushing a quantity to Stripe on every invitation was rejected and the reason is worth keeping: seats include pending invitations, an invitation expires on a clock, and there is no scheduler — so the quantity would drift from the truth with no code running. The cost is deliberate and is a product decision, not an oversight: **adding somebody to a full plan is two steps, buy then invite.** And **a downgrade removes nobody** — eight members stay when the plan drops to one seat; only the ninth invitation is refused. Because one published form is not a workable development environment, and because a one-seat plan cannot invite anybody, **`DEV_PLAN_KEY` forces every organization onto one plan** — `dev` for no limits at all, or `free`/`pro`/`team` to drive the limit screens on purpose. It is temporary, it is honoured **only when `NODE_ENV` is exactly `development` or `test`** (an allowlist, so a missing `NODE_ENV` enforces limits rather than lifting them), and the three test configurations pin it off because `app.ts` loads `.env` into every suite ([08-operations](docs/sot/08-operations.md)). **Billing is built, all three plans** ([`features/0013`](features/0013-stripe-subscriptions.md), Free ↔ Pro; [`features/0015`](features/0015-team-plan-and-purchased-seats.md), Team and its seats). `Subscription` records the Stripe relationship and `StripeEvent` is what makes the webhook idempotent — its primary key *is* Stripe's `event.id`, because delivery is at-least-once. `backend/src/services/stripe.ts` is the **only** module that imports the Stripe SDK, and it is the **only** writer of `Organization.planKey`, which stayed exactly where it was: `getEntitlements`, `effectivePlan` and `assertCanPublishForm` were not changed at all, so no limit check joins a billing table and there is one answer to "which plan is this?". Five things about it are easy to get wrong. The **webhook is mounted above `app.use(express.json())`** and must stay there — Stripe signs the raw bytes, and under the JSON parser every signature check fails silently and totally, leaving subscriptions bought and never activated. **Returning from Checkout is not proof of payment**; nothing grants a plan except the webhook, and the Settings screen only says activation is in progress and re-reads entitlements. **The handler is state-setting, never incremental** — it writes what the event says, which is what makes it safe under replay and reordering. **A downgrade unpublishes nothing and deletes nothing**: five published forms stay published on a drop to free, and only the sixth is refused. And **`past_due` keeps the paid plan**, because Stripe retries for days and cutting someone off over an expired card is premature; the status→plan map is an allowlist, so a status this code has never heard of falls to free. Prices are **not** in the code and never will be — the amount lives in Stripe, the application stores a price id (`STRIPE_PRICE_PRO`), and no screen renders a figure that did not come from the API. All three Stripe variables are optional: unset means billing is simply off and the routes answer `503`. **`DEV_PLAN_KEY` wins over a real subscription**, so it must be empty when testing billing. Two more things 0014 closed: the webhook now logs when an event arrives in an API version this code was not written against — and **processes it anyway**, because refusing would make Stripe retry until it disabled the endpoint — and `POST /api/billing/checkout` is serialised per organization by an in-process lock (`services/organization-lock.ts`, which explains why not `SELECT … FOR UPDATE`) and hands back an already-open Checkout Session rather than opening a second one. `STRIPE_PRICE_TEAM` is the fourth optional Stripe variable and unset means Team is simply not for sale — Free and Pro are unaffected. Two pieces of the design live in Stripe's **portal configuration** rather than in this repository, and without them the feature does not work as designed: *Update quantities* (which is how a seat is bought at all) and *Switch plan* with both products, with downgrades scheduled at the period end to match `planKeyForStatus` ([08-operations](docs/sot/08-operations.md)). There is no plan picker in the SPA and there should not be — switching an existing subscription is the portal's job. **There is a public API now, and it is read-only** ([`features/0019`](features/0019-api-keys-and-read-only-public-api.md)): `/api/v1` is authenticated by an API key that belongs to an **organization and to no user**, which is why it is its own router (`backend/src/routes/v1/`) scoping on `organizationId` rather than a flag on the middleware that resolves a `Membership` — giving a key a user id would tie a customer's integration to one employee. Four things about it. **`/api/v1` is a contract and everything else under `/api/*` is internal**, so v1 bodies are built explicitly rather than serialised from Prisma rows. **The key is a revocable row, not a token**: SHA-256 of a 32-byte secret (never bcrypt — it is verified on every request), shown once at creation, and read from the database per request so revoking works on the next call. **Its limiter counts per key, not per IP**, falling back to the address when there is no valid key — and the middleware order is identify, limit, *then* require, because rejecting first means an unauthenticated caller never reaches the limiter. And **`hasApiAccess` is Team-only**, so a Free or Pro organization minting a key gets a `402`. There is no SPA screen for keys yet, so a customer cannot mint one from the product. **Outbound webhooks are built** ([`features/0020`](features/0020-outbound-webhooks.md)), which closes the build order: `response.created` is signed `t=…,v1=…` over `<timestamp>.<raw body>`, delivered by a second job type on the queue, and recorded in a delivery log. Four things about it are easy to get wrong. **`backend/src/services/webhook-egress.ts` is the only module that may request a customer-supplied URL** — before this feature there was no outbound HTTP in the backend at all, and a naive `fetch(endpoint.url)` is SSRF into the deployment's own network: it requires https, resolves and checks every address, **connects to the address it checked** (two resolutions is a DNS-rebinding hole) and refuses redirects, re-checking on every delivery and not only at configuration. **The queue is not optional here**, unlike the embed: the event source is a respondent's submission, so inline delivery would put a third party's server on the critical path of pressing "submit" — configuring an endpoint without `REDIS_URL` or `WEBHOOK_SIGNING_KEY` answers `503` rather than accepting something undeliverable. **The endpoint secret is encrypted, not hashed**, because it has to be used to sign; that protects a leaked backup and nothing against a compromised process, and it is why a missing key refuses rather than storing plaintext. And **the delivery log holds no payload bodies**, because they carry respondent answers and would outlive the form they came from. There is no tax handling, and no email delivery, structured logging or lint — so a customer whose endpoint gets auto-disabled after ten failures is not told, and there is no SPA screen for keys or webhooks yet. **The visual design is built** except for its commercial parts — the canvas is recorded with its tokens in [`05-frontend-patterns §8`](docs/sot/05-frontend-patterns.md), and what it draws that the app does not have is listed there: the prices (which are deliberately permanent — no amount is rendered from a constant anywhere), the organization switcher, the API keys tab, and the landing page. The landing's technology is an open decision, laid out in [`02-architecture`](docs/sot/02-architecture.md).
